\section{Overview}
% ============================================================

The AI image generation pipeline is an autonomous system that accepts a
natural language prompt and iteratively generates, scores, and refines
images until a candidate meeting all quality thresholds is accepted by a
tactical large language model (LLM).

A browser-based pipeline UI at \texttt{http://localhost:12000} provides the
primary operator interface: create and resume creative workflows, watch images
arrive in a live gallery as they are generated and scored, send thumbs
up/down feedback, and chat with the tactical LLM to refine creative direction.
The UI backend is a Spring Boot application serving a single-page frontend
and streaming gallery events to the browser over WebSocket.

The pipeline is designed around three principles:

\begin{enumerate}
  \item \textbf{Observable}: every message and verdict flows through
        inspectable queues. Artemis's management console provides real-time
        visibility into all message flows. Dead-letter messages accumulate in
        \texttt{pipeline.dead} for operator review. The browser UI streams
        image and decision events live.
  \item \textbf{Scalable}: the Spring Boot pipeline, scorer sidecars, and LLM
        servers are independently deployable. The message broker decouples
        the generation and scoring tiers; scorer capacity scales horizontally.
  \item \textbf{Persistent}: every generated image, its scorer results, and
        all decision context are recorded in PostgreSQL. The strategic LLM
        reads this history across sessions to identify patterns and refine
        creative direction.
\end{enumerate}

The pipeline supports three GPU backends. Choose the row that matches your
hardware:

\begin{center}

\midrule

                    & System RAM      & 32\,GB             & 64\,GB \\

(80B total, $\sim$3B active per forward pass) served via \texttt{mlx\_lm.server}.
See Section~\ref{sec:memory} for the per-component breakdown.

\section{Component Architecture}
% ============================================================

\subsection{Design}

The Spring Boot pipeline is the sole message-driven component. It contains
four internal workers, each responsible for a distinct phase of the loop:

\begin{description}
  \item[\texttt{ComfyUiWorker}] Listens on \texttt{loop.generate},
        \texttt{loop.retry}, and \texttt{loop.inpaint}. Submits the workflow
        to ComfyUI via HTTP/WebSocket. On completion publishes to
        \texttt{loop.generated} and fires an \texttt{image\_ready} WebSocket
        event via \texttt{GalleryBroadcastService}.
  \item[\texttt{Scorer}] Listens on \texttt{loop.generated}. Calls the three
        scorer sidecars sequentially via HTTP. Applies two-level threshold logic
        in Java (CLIP score, then artifact confidence). Records results in
        PostgreSQL. Publishes passing candidates to \texttt{loop.verdicts} with
        full VLM dimension scores, issues, and recommendations; rejected images
        are written to PostgreSQL but not published.
  \item[\texttt{TacticalLlmCaller}] Listens on \texttt{loop.verdicts}. Runs
        a full agentic loop: builds context from PostgreSQL, calls the tactical
        LLM server with tool definitions (\texttt{analyze\_image} via VLM
        sidecar), and handles the decision. Retry decisions (and inpaint decisions,
        which are downgraded to retry) publish to \texttt{loop.retry}. Accept writes
        to PostgreSQL. Escalate writes a \texttt{pipeline\_events} row and
        shuts down the Loop cleanly. Fires \texttt{decision} events via
        \texttt{GalleryBroadcastService}.
  \item[\texttt{GalleryBroadcastService}] In-process WebSocket broadcast.
        Called directly by \texttt{ComfyUiWorker} and
        \texttt{TacticalLlmCaller}. No broker involvement.
\end{description}

The three scorer sidecars (\texttt{clip\_scorer.py},
\texttt{artifact\_scorer.py}, \texttt{vlm\_scorer.py}) are stateless HTTP
services. They hold their model weights in memory but have no connection to
the message broker.

\section{Address and Queue Topology}
% ============================================================

All pipeline addresses use anycast routing (queue semantics: one consumer
receives). There are no multicast (topic) addresses --- WebSocket broadcast
to browsers is handled in-process by \texttt{GalleryBroadcastService}.

\begin{center}
\begin{tabular}{llll}
\toprule
\textbf{Address} & \textbf{Protocol} & \textbf{Publisher} & \textbf{Consumer} \\
\midrule
\texttt{loop.generate}  & AMQP~1.0 & WorkflowController, ChatWsHandler & ComfyUiWorker \\
\texttt{loop.generated} & AMQP~1.0 & ComfyUiWorker                     & Scorer \\
\texttt{loop.verdicts}  & AMQP~1.0 & Scorer (candidates only)          & TacticalLlmCaller \\
\texttt{loop.retry}     & AMQP~1.0 & TacticalLlmCaller                 & ComfyUiWorker \\
\texttt{loop.inpaint}   & AMQP~1.0 & (none — not implemented)          & ComfyUiWorker \\
\texttt{pipeline.dead}  & AMQP~1.0 & (DLX from all queues)             & (none; Artemis console) \\
\bottomrule
\end{tabular}
\end{center}

Images rejected by the cascade threshold logic are written to PostgreSQL
with \texttt{verdict = 'rejected'} and a \texttt{rejection\_reason} field
(\texttt{clip\_threshold} or \texttt{artifact\_threshold}) but are not
published to any queue.
The \texttt{loop.retry} address carries the same JSON schema as
\texttt{loop.generate} with revised prompt / workflow params.
\texttt{loop.inpaint} is registered but receives no messages (not yet implemented).

\section{Data Flow}
% ============================================================

\begin{enumerate}
  \item The operator opens the browser UI at \texttt{http://localhost:12000}.
        They create a conversation and workflow via the REST API (Spring Boot
        pipeline writes to PostgreSQL). Clicking \textbf{Generate} causes
        \texttt{WorkflowController} to publish a generation request to
        \texttt{loop.generate} carrying the \texttt{workflow\_id},
        \texttt{conversation\_id}, \texttt{session\_uuid}, and prompt.

  \item \texttt{ComfyUiWorker} receives the \texttt{loop.generate} message,
        inserts a \texttt{pending\_generations} row (Narayana JTA), submits
        the ComfyUI workflow via HTTP, and polls for completion via WebSocket.

  \item On completion, \texttt{ComfyUiWorker} publishes to
        \texttt{loop.generated} and calls \texttt{GalleryBroadcastService}
        to push an \texttt{image\_ready} WebSocket event to the browser.

  \item \texttt{Scorer} receives from \texttt{loop.generated} and calls all
        three scorer sidecars sequentially via HTTP:
        \begin{itemize}
          \item \texttt{POST http://localhost:12002/score} (CLIP scorer)
          \item \texttt{POST http://localhost:12003/score} (artifact scorer)
          \item \texttt{POST http://localhost:12004/score} (VLM scorer)
        \end{itemize}
        It also queries PostgreSQL for the active north star embedding and
        computes a cosine similarity score via the pgvector extension
        (\texttt{north\_star\_similarity}).

  \item Threshold evaluation in \texttt{Scorer.java}:
    \begin{itemize}
      \item CLIP score below \texttt{scoring.clip-threshold}: write rejected
            record to PostgreSQL with \texttt{rejection\_reason = clip\_threshold}; stop.
      \item Artifact confidence above \texttt{scoring.artifact-threshold}: same,
            \texttt{rejection\_reason = artifact\_threshold}; stop.
      \item Both within bounds: write candidate record to PostgreSQL, publish
            to \texttt{loop.verdicts} with full scorer results. VLM scores are
            always forwarded --- the tactical LLM decides what to do with them.
    \end{itemize}

  \item \texttt{TacticalLlmCaller} receives the verdict from
        \texttt{loop.verdicts}, loads conversation context from PostgreSQL
        (recent chat messages, feedback, north star, session direction), and
        runs the agentic decision loop:
    \begin{enumerate}
      \item Builds system prompt (context + north star + taste synthesis).
      \item Calls \texttt{mlx\_lm.server} at port 12001 with tool definitions
            (\texttt{analyze\_image}). Thinking mode is \textbf{off by default}
            (\texttt{/no\_think}); it is enabled only for genuinely borderline
            images (VLM mean 4.5--7.5 \textit{and} CLIP $\geq$ 0.20) where
            extended reasoning could change the outcome.
      \item If the LLM emits \texttt{analyze\_image} tool calls: executes
            \texttt{POST http://localhost:12004/analyze} and appends results.
      \item Re-prompts until the LLM emits a final decision JSON or the tool
            iteration cap is reached. A first-pass \texttt{escalate} with
            thinking off triggers a second pass with thinking enabled.
    \end{enumerate}

  \item Decision handling in \texttt{TacticalLlmCaller}:
    \begin{description}
      \item[\texttt{accept}] Writes accepted image record to PostgreSQL.
            Fires \texttt{decision} WebSocket event via
            \texttt{GalleryBroadcastService}.
      \item[\texttt{retry}] Publishes to \texttt{loop.retry} with revised
            prompt and/or workflow params. Increments retry counter in
            PostgreSQL budget table.
      \item[\texttt{inpaint}] Not yet implemented. \texttt{TacticalLlmCaller}
            downgrades to \texttt{retry} and publishes to \texttt{loop.retry}.
      \item[\texttt{give\_up}] Writes give-up record to PostgreSQL. No further
            messages published.
      \item[\texttt{escalate}] Writes a \texttt{pipeline\_events} row
            (\texttt{type = 'mode\_switch\_requested'}) and calls
            \texttt{SpringApplication.exit()} to shut down the Loop cleanly.
            If \texttt{loop.sh} was started with \texttt{--auto-escalate}, the
            background monitor detects the pipeline exit, finds the pending
            escalation in \texttt{pipeline\_events}, and starts
            \texttt{strategic.sh} automatically. Without that flag the operator
            starts \texttt{strategic.sh} manually; either way,
            \texttt{StrategicLlmCaller} auto-detects the pending escalation.
    \end{description}
\end{enumerate}

\section{Persistence Layer}
% ============================================================

\subsection{PostgreSQL Schema}

The pipeline uses a Flyway-managed PostgreSQL database with the pgvector
extension for CLIP embeddings. Schema is applied in migrations V1--V4 under
\texttt{pipeline/src/main/resources/db/migration/}.

\subsubsection{Core tables}

\begin{description}
  \item[\texttt{conversations}] Named creative projects. Parent of all workflows.
  \item[\texttt{workflows}] A stable creative direction within a conversation.
        Carries \texttt{workflow\_path}, \texttt{max\_retries},
        \texttt{max\_inpaints}, and \texttt{budget\_policy} (fresh $|$ accumulated).
  \item[\texttt{images}] One row per generated image. Key columns:
        \texttt{image\_uuid}, \texttt{session\_uuid}, \texttt{sequence\_number},
        \texttt{workflow\_id}, \texttt{conversation\_id}, \texttt{image\_path},
        \texttt{verdict} (candidate $|$ rejected),
        \texttt{rejection\_reason} (clip\_threshold $|$ artifact\_threshold),
        \texttt{decision} (accepted $|$ retry $|$ inpaint $|$ give\_up),
        \texttt{clip\_score}, \texttt{artifact\_score},
        \texttt{vlm\_scores JSONB}, \texttt{vlm\_issues TEXT[]},
        \texttt{vlm\_recs TEXT[]},
        \texttt{embedding vector(512)}, \texttt{north\_star\_similarity float}.
  \item[\texttt{budget}] Per-run retry and inpaint budget counters keyed by
        \texttt{session\_uuid}.
  \item[\texttt{chat\_messages}] Chat history between the operator and the
        tactical LLM, scoped per conversation.
  \item[\texttt{user\_feedback}] Thumbs up/down ratings with optional comment,
        scoped per image and workflow.
\end{description}

\subsubsection{Pending-work tables (XA staging)}

Three tables serve as transactional staging rows within Narayana JTA
transactions, preventing message loss across restarts:

\begin{description}
  \item[\texttt{pending\_generations}] Written by \texttt{ComfyUiWorker}
        inside the JMS transaction before submitting to ComfyUI. Cleaned up
        on successful completion.
  \item[\texttt{pending\_scorings}] Written by \texttt{Scorer} inside the
        JMS transaction before calling scorer sidecars.
  \item[\texttt{pending\_decisions}] Written by \texttt{TacticalLlmCaller}
        inside the JMS transaction before calling the LLM.
\end{description}

\subsubsection{Strategic context tables}

\begin{description}
  \item[\texttt{north\_star}] The active creative goal. One row per revision.
        Superseded rows have \texttt{superseded\_at} set. Contains
        \texttt{content text} and \texttt{embedding vector(512)} (CLIP text
        encoding of the north star, used for \texttt{north\_star\_similarity}
        queries).
  \item[\texttt{session\_direction}] Tactical guidance for the current
        workflow run, written by the strategic LLM.
  \item[\texttt{taste\_synthesis}] Accumulated aesthetic preferences derived
        from user feedback, written by the tactical LLM via \texttt{TasteService}
        when the feedback count threshold (\texttt{taste.synthesis-threshold},
        default~5) is reached.
  \item[\texttt{pipeline\_events}] Mode switch signalling. Written by
        \texttt{TacticalLlmCaller} on \texttt{escalate} decision
        (\texttt{type = 'mode\_switch\_requested'}). Read by the
        orchestration layer (\texttt{loop.sh} monitor or the operator) to
        decide when to start the Strategic super-component.
\end{description}

\subsection{Conversation and Workflow Hierarchy}

The data model is a four-level hierarchy:

\[
\texttt{conversation} \;\to\; \texttt{workflow} \;\to\; \texttt{run (session\_uuid)} \;\to\; \texttt{image\_uuid}
\]

\begin{description}
  \item[Conversation] Persistent across the life of a creative project. Owns
        the chat history. Multiple workflows may exist within one conversation.
  \item[Workflow] A stable creative direction (subject matter, workflow file,
        budget policy). A workflow is \textit{resumed} to start a new run;
        the workflow record itself is never replaced.
  \item[Run] One invocation of the generation loop. Corresponds to a
        \texttt{session\_uuid}. Each run has its own \texttt{budget} row.
  \item[Image] One generated image within a run. Corresponds to an
        \texttt{image\_uuid} in the \texttt{images} table.
\end{description}

\section{Data-Loss Protection}
% ============================================================

\subsection{Narayana JTA Transactions}

All message-to-database writes use Narayana JTA (XA) transactions. The JMS
message receive and the PostgreSQL write are committed atomically. On crash
recovery, Narayana rolls back any prepared-but-not-committed XA transactions
on startup.

The three pending-work tables (\texttt{pending\_generations},
\texttt{pending\_scorings}, \texttt{pending\_decisions}) act as durable
staging: each worker inserts a row in the JTA transaction. On restart, the
pipeline can detect and resume in-flight work.

\subsection{Dead Letter Exchange}

All pipeline queues declare \texttt{x-dead-letter-address: pipeline.dead}.
Failed or expired messages accumulate in \texttt{pipeline.dead} for operator
review via the Artemis management console at \texttt{http://localhost:12009}.

\section{Operations}
% ============================================================

\subsection{Starting the Pipeline}

\begin{lstlisting}[style=shell]
# Start middleware first (K3s workloads + port-forwards)
$SOXHLET_ROOT/middleware.sh start

# Start the Loop super-component
$SOXHLET_ROOT/loop.sh start

# Or with autonomous escalation handoff enabled:
$SOXHLET_ROOT/loop.sh start --auto-escalate
\end{lstlisting}

The optional \texttt{--auto-escalate} flag forks a background monitor after
startup. When the pipeline exits due to a tactical \texttt{escalate} decision,
the monitor finds the pending \texttt{pipeline\_events} row and starts
\texttt{strategic.sh} without operator intervention. Without this flag,
\texttt{loop.sh start} returns after all components are healthy and the
operator controls the escalation handoff manually. The flag is intentionally
per-invocation: there is no persistent auto-escalation state, which prevents
runaway mode-switch cycles if the pipeline crashes unexpectedly.

\texttt{loop.sh} starts components in dependency order:

\begin{enumerate}
  \item Middleware health check (Artemis on 12008, PostgreSQL on 12007).
  \item \textbf{Parallel}: ComfyUI (port 12006) and tactical LLM server
        (\texttt{mlx\_lm.server} on port 12001).
  \item Scorer sidecars: clip (12002), artifact (12003), vlm (12004).
  \item Spring Boot pipeline (port 12000).
\end{enumerate}

Individual component scripts:

\begin{lstlisting}[style=shell]
$SOXHLET_ROOT/loop/comfyui.sh start
$SOXHLET_ROOT/loop/tactical_llm.sh start

source $SOXHLET_ROOT/loop/scorers/venv/bin/activate
python $SOXHLET_ROOT/loop/scorers/clip_scorer.py
python $SOXHLET_ROOT/loop/scorers/artifact_scorer.py
python $SOXHLET_ROOT/loop/scorers/vlm_scorer.py
\end{lstlisting}

\section{Threshold Calibration}
% ============================================================

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Property (\texttt{config.yaml})} & \textbf{Default} & \textbf{Semantics} \\
\midrule
\texttt{scoring.clip-threshold}     & 0.25 & Reject in Scorer if CLIP score $< 0.25$ \\
\texttt{scoring.artifact-threshold} & 0.50 & Reject in Scorer if AI confidence $> 0.50$ \\
\bottomrule
\end{tabular}
\end{center}

These are the only two Scorer-level gates. VLM dimension scores are not
thresholded in the Scorer --- all CLIP- and artifact-passing candidates are
forwarded to \texttt{TacticalLlmCaller} so the tactical LLM can diagnose
specific failures and issue targeted retry or inpaint decisions.

All values are placeholders. Calibration procedure:

\begin{enumerate}
  \item Run the loop permissively (\texttt{scoring.clip-threshold: 0.0},
        \texttt{scoring.artifact-threshold: 1.0}).
  \item Query the \texttt{images} PostgreSQL table and examine score
        distributions across accepted and rejected images.
  \item Set \texttt{scoring.clip-threshold} at the point below which the
        tactical LLM consistently retries without improvement.
  \item Set \texttt{scoring.artifact-threshold} at the point above which
        photorealism scores are consistently poor.
  \item Iterate: thresholds too aggressive waste good candidates; too permissive
        waste tactical LLM compute.
\end{enumerate}

Threshold values are injected via Spring Boot's \texttt{@Value} annotation from
\texttt{application.yml} (or environment variable overrides).
No code changes are required for recalibration.

\section{Scale-Out Path}
% ============================================================

\begin{description}
  \item[Multiple ComfyUI workers] Run multiple Spring Boot pipeline instances
        with competing consumers on \texttt{loop.generate} and
        \texttt{loop.generated}. Artemis anycast distributes work across
        consumers.
  \item[Remote scoring nodes] Deploy scorer sidecars on separate machines and
        update \texttt{sidecars.*.host} in \texttt{config.yaml}. The pipeline
        calls them via HTTP; no broker reconfiguration needed.
  \item[Managed broker] Migrate to Amazon MQ for ActiveMQ (AMQP~1.0
        compatible). Update \texttt{broker.url} in \texttt{config.yaml}.
  \item[Strategic LLM for chat] The chat WebSocket calls the tactical LLM
        by default. Future: route chat to the strategic model by updating
        the chat handler's LLM client configuration.
\end{description}
